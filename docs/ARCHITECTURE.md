# Architecture

```text
Compose UI
  ↓
ViewModels / use-case-shaped services
  ↓
Model Manager · Room repositories · local ingestion · retrieval · policy
  ↓
InferenceRuntimeRegistry
  ├── LlamaCppInferenceRuntime (GGUF)
  └── LiteRtLmInferenceRuntime (LITERT_LM) → Messenger → :litert service → Engine/Conversation/MessageCallback
  ↓
llama.cpp Android JNI module · pinned LiteRT Kotlin client + official 0.17.1 native libraries · SQLite FTS4 · ContentResolver / app-private files
```

`app` owns product/domain behavior. `llama-runtime` owns the Android binding copied from the pinned llama.cpp Android example and exposes only the binding API to the product adapter. `LlamaCppInferenceRuntime` maps GGUF metadata and streaming tokens into product-owned data classes. `LiteRtLmInferenceRuntime` is an adapter over the official LiteRT-LM `Engine`/`Conversation` API; it validates the native LiteRT-LM container and maps its declared modalities and benchmark info without inventing unavailable values.

`ModelDescriptor` is the persistence/UI contract. Its format, runtime, source, capabilities, accelerators, auxiliary files and import status are independent of llama.cpp. A multimodal GGUF record stores the primary model and projector descriptors together; a projector is not exposed as a separate model. Binaries are copied or downloaded through a staging path and only inserted into the library after validation and atomic finalization.

LiteRT JNI runs in a non-exported separate process. The client uses an IPC HandlerThread, executor-delivered binding callbacks and an independent deadline timer, with no Main dependency for worker termination. Android elapsed realtime includes sleep; bounded partial wake leases apply only to explicitly requested operations. The native worker has separate cancellation and diagnostic observers; checkpoints, hash bytes and sampled RAM/Java stack travel over checked IPC. Tagged error diagnostics reuse the existing message generationMetrics column and are distinct from benchmarks. Generation events include state/error/cancel as well as tokens/metrics/completion. Room remains in the main process, schema version 2. See [LITERT_DIAGNOSTICS.md](LITERT_DIAGNOSTICS.md) for timing and physical-validation boundaries.

The Hugging Face client is intentionally outside inference. It accepts only HTTPS `huggingface.co` repository references, sanitizes paths, filters the file tree to recognized model/auxiliary files by default and streams downloads to a controlled private `.partial` file. The optional token is encrypted using an Android Keystore AES-GCM key.

Heavy work is dispatched off the main thread. Native operations are serialized per runtime. The vendored llama.cpp binding still reloads between turns because its system-prompt lifecycle is load-scoped. LiteRT retains one initialized Engine when verified file identity and engine configuration match. Since 0.1.6, completed normal text conversations also retain their native KV state only when the exact budgeted history, system instruction, sampler and output configuration match and real getTokenCount plus a conservative next-input allowance fit context. Only the new user message is then sent. Dropped/changed history or evidence, changed settings, errors and cancellation discard the conversation; unsafe/native-error paths still discard the engine. Smoke always creates a fresh engine but uses the private disk weight cache. Missing load/session timings stay null, while engineReused/sessionReused/prepareMs expose the actual branches. See [CPU stabilization contract](LITERT_CPU_STABILITY_016.md).

Room relationships are explicit. Documents and model files are copied into app-private storage and retain their originating URI; deleting workspace data therefore does not delete externally-owned files. FTS uses an external-content table keyed by the segment row ID. Room migration 1→2 adds runtime-neutral model fields and maps legacy GGUF rows to `LLAMA_CPP` by their existing runtime ID.

The orchestration prompt labels system policy, user instructions, memory and retrieved documents separately. Retrieved content is always untrusted data and cannot authorize tools. Runtime-neutral ConversationPrompt/ChatMessage coexist with the GGUF text fallback. Restored LiteRT history uses the embedded template/processor's actual role: Qwen/generic ChatML requires assistant, whereas model remains available for legacy processors. The additive Role.ASSISTANT factory in litert-compat preserves the upstream Message.model API, JNI names and all other source files; the official native AAR is unchanged. The current user is sent once and the model owns template rendering. Ordinary structured chat disables thinking without changing capability metadata. Actual repeat penalty plus an eight-token no-repeat window prevent exact decode loops when enabled; the fallback detector also notices interleaved substantial paragraphs and requests native cancellation with a five-second reset deadline. Failed partial turns remain in Room but are excluded from inference history. requestTtftMs includes preparation; generation-only ttftMs does not. LiteRT onDone is reported separately from unsupported literal EOS/finish reason, including an actual decode-count output-cap flag.

Since 0.1.7, RuntimePreparation starts actual eligible LiteRT CPU load/session work on chat entry or selection, without generating a warmup prompt. Readiness requires load completion. Send awaits pending preparation; cancellation and model replacement wait for native teardown before further work. Progress errors are recorded and old/stale callbacks cannot mark the new model ready. The composer remains usable during preparation. Chat exit still unloads the runtime, so this overlaps rather than eliminates cold initialization.

GenerationMetricsPresentation keeps existing benchmark storage separate from model text and parses legacy comma-decimal records. Details exposes measured values, with raw fields behind an explicit expansion. Only actual outputLimitReached=true displays the cutoff warning and enables Continue on the latest completed turn. Continue is a visible new user instruction through the usual runtime path. An app status note tells the next prompt that missing text was never generated; the original partial reply stays intact. Changed trusted context safely rebuilds the conversation while retaining a compatible engine. Native completion, literal EOS and semantic answer completeness remain distinct. The actual INT8 reference still fails missing-point and continuation-language checks; status context is not proof of model compliance. See [0.1.7 evidence and limits](CHAT_LATENCY_AND_OUTPUT_017.md).

Room remains schema 2. LiteRtChatDefaultsUpgrade wraps the existing LiteRtDefaultsUpgrade and uses a separate private one-time marker. The exact original CPU512/repeat1.0 tuple first follows the old128/repeat1.1 correction; the exact prior CPU128/.3/.95/40/repeat1.1/seed0 default then becomes256. Other custom tuples and all GGUF rows remain intact, including subsequent explicit returns to128 or disabled controls. Exact manually chosen default tuples cannot be distinguished. No destructive migration is used. A higher output ceiling gives lists more room but can increase long-reply latency; it does not accelerate native decoding.
